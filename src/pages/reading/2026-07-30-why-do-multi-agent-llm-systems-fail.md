### 一句话定位

> 论文试图回答的不是“多智能体系统成功率是多少”，而是“它具体以什么方式失败”。

------

# 0. 摘要核心翻译

当前多智能体LLM系统受到广泛关注，但它们相对单智能体或简单采样方法的性能提升经常很有限。为了系统理解这些系统为什么失败，作者提出：

1. 包含1642条执行轨迹的 **MAST-Data**；
2. 包含14种失败模式的 **MAST分类体系**；
3. 基于o1的 **LLM-as-a-Judge自动标注流程**。

14种失败模式被归入三类：

- 系统设计问题；
- 智能体间失配；
- 任务验证问题。

作者进一步比较不同模型、任务和多智能体架构的失败分布，并表明很多失败并非只能归因于基础模型能力，而与工作流、角色设计、信息传递和验证机制密切相关。

------

# 1. 方法动机

## 1.1 为什么研究“失败模式”？

作者发现，当前主流多智能体系统在不同基准上的失败率约为 **41%—86.7%**。

但传统Benchmark通常只提供：

- 最终任务是否成功；
- 准确率或完成率；
- 系统总体得分。

它们难以回答：

- 错误发生在哪个阶段；
- 哪个交互行为导致失败；
- 是模型、工作流、角色、通信还是验证问题；
- 系统修改后具体减少了哪类失败。

因此，作者希望将评估从：

```
任务成功 / 任务失败
```

推进到：

```
失败发生在哪里
→ 以什么行为表现
→ 属于哪类重复模式
→ 应该修改哪个设计环节
```

------

## 1.2 现有方法的不足

### 只有总体指标，没有失败解释

两个系统可能具有相同成功率，但内部问题完全不同：

- 一个经常偏离任务；
- 一个经常重复步骤；
- 一个生成结果正确，但验证器不可靠。

仅看成功率无法指导系统改进。

### 缺少统一失败语言

不同研究可能把同一问题称为：

- 协调失败；
- 上下文错误；
- 信息遗漏；
- 规划失效；
- Agent幻觉。

没有统一定义，就难以跨系统比较。

### 多智能体失败具有传播性

一个典型失败链可能是：

```
Agent A遗漏信息
→ Agent B没有询问
→ Agent C基于错误假设执行
→ Verifier没有发现
→ 最终任务失败
```

因此不能只看最终答案，必须分析完整轨迹。

### 人工分析成本高

初始轨迹平均超过15000行文本。完全依靠人工无法扩展到1600多条数据。

------

## 1.3 研究直觉

论文的核心直觉是：

> 多智能体失败不是完全随机的，而是存在可跨模型、跨任务、跨框架重复观察的模式。

同时：

MAS可靠性=基础模型能力+系统设计+智能体协调+验证机制\text{MAS可靠性} = \text{基础模型能力} + \text{系统设计} + \text{智能体协调} + \text{验证机制}MAS可靠性=基础模型能力+系统设计+智能体协调+验证机制

因此，即使不更换底层LLM，只修改角色、拓扑、终止条件和验证流程，也可能改善性能。

------

# 2. 方法设计

## 2.1 总体Pipeline

```
收集执行轨迹
→ 人工发现重复失败行为
→ 建立MAST失败分类
→ 检验不同标注者是否理解一致
→ 用少量人工案例校准o1
→ 批量标注更多轨迹
→ 构建MAST-Data并分析失败分布
```

------

## 2.2 第一步：收集初始轨迹

作者首先收集150条轨迹，来自五个多智能体框架：

- HyperAgent；
- AppWorld；
- AG2；
- ChatDev；
- MetaGPT。

任务主要包括：

- 编程；
- 数学问题求解。

这些系统具有不同组织形式：

| 系统       | 主要结构                     |
| ---------- | ---------------------------- |
| MetaGPT    | 基于SOP的软件开发流水线      |
| ChatDev    | 分层软件开发流程             |
| HyperAgent | Planner协调专业子Agent       |
| AppWorld   | Supervisor连接多个服务Agent  |
| AG2        | 可自定义对话和终止机制的框架 |

作者有意选择结构不同的系统，以减少分类只适用于单一框架的风险。

------

## 2.3 第二步：使用扎根理论发现失败模式

作者采用 **Grounded Theory，扎根理论**，从真实执行轨迹中逐步归纳失败类别。

具体包括：

1. **开放编码**：给观察到的失败行为贴临时标签；
2. **持续比较**：比较不同轨迹中的相似和不同现象；
3. **备忘录记录**：记录类别边界和修改理由；
4. **理论化**：把临时标签整理成正式分类；
5. **理论饱和**：继续分析数据时，很少再出现新的重要类别。

------

## 追问一：扎根理论是不是仍然在“凭直觉分类”？

### 回答

**本质上仍然包含研究者的主观判断。**

失败类别不会自动从数据中产生，而是专家阅读数据后进行解释、命名、合并和拆分。

扎根理论与“纯凭直觉列清单”的区别是：

| 纯直觉分类         | 扎根理论式分类             |
| ------------------ | -------------------------- |
| 看数据前就确定类别 | 先阅读数据，再形成类别     |
| 主要依赖个人经验   | 每个类别需要真实案例支持   |
| 很少修改           | 持续合并、拆分和修订       |
| 不强调反例         | 比较正例、反例和边界案例   |
| 一个人认为合理即可 | 多名专家独立标注并讨论     |
| 难以复现           | 通过一致性指标检查可重复性 |

更准确地说，论文做的是：

> **专家基于数据进行主观但程序化的归纳分类，再验证这套分类能否被不同标注者稳定使用。**

### Cohen’s κ=0.88验证了什么？

它主要说明：

> 不同标注者能够较一致地使用MAST定义。

但它不证明：

- 14种类别是唯一正确的；
- 分类覆盖全部MAS失败；
- 类别对应真正的因果根因；
- 换一批专家仍会得到完全相同的分类。

因此：

高一致性≠分类客观真理\text{高一致性}\neq\text{分类客观真理}高一致性=分类客观真理

而更接近：

高一致性≈定义清楚且可重复使用\text{高一致性}\approx\text{定义清楚且可重复使用}高一致性≈定义清楚且可重复使用

------

## 2.4 第三步：建立并校准MAST

作者通过三轮标注者一致性实验修订分类：

```
3名专家分别标注5条轨迹
→ 比较分歧
→ 修改、合并或拆分类别
→ 再次独立标注
```

最终达到：

κ=0.88\kappa=0.88κ=0.88

说明MAST的定义具有较高可操作性。

# 3. MAST：三大类别与十四种失败模式

## FC1：系统设计问题，占44.2%

这类失败通常由系统架构、提示词规范、角色设计或状态管理缺陷引起。问题往往在执行前已经埋下，在任务执行过程中表现出来。

| 编号   | 失败模式       | 含义                                     | 比例  |
| ------ | -------------- | ---------------------------------------- | ----- |
| FM-1.1 | 不服从任务规范 | 忽略任务要求、约束或输出条件             | 11.8% |
| FM-1.2 | 不服从角色规范 | 未履行自身职责或超出角色权限             | 1.5%  |
| FM-1.3 | 步骤重复       | 重复已经完成的推理、搜索或工具调用       | 15.7% |
| FM-1.4 | 对话历史丢失   | 忽略近期交互，退回较早的对话状态         | 2.8%  |
| FM-1.5 | 不知道终止条件 | 无法识别任务已经完成、无法完成或应当停止 | 12.4% |

### 简要现象与原因

主要表现为**步骤重复、无法识别终止条件和违反任务要求**。这些失败既可能来自模型的指令遵循与上下文理解不足，也可能源于**工作流设计不清、角色与决策权限模糊、终止条件缺失以及状态管理不可靠**。

------

## FC2：智能体间失配，占32.3%

这类失败发生在多个智能体协作过程中，核心问题是关键信息没有被正确传递、理解、采纳或转化为行动。

| 编号   | 失败模式          | 含义                                     | 比例  |
| ------ | ----------------- | ---------------------------------------- | ----- |
| FM-2.1 | 对话重置          | 无必要地重新开始对话，丢失已有进展       | 2.2%  |
| FM-2.2 | 未请求澄清        | 信息模糊时不询问，而是基于假设继续执行   | 6.8%  |
| FM-2.3 | 任务偏离          | 逐渐偏离原始目标，转而解决错误问题       | 7.4%  |
| FM-2.4 | 信息隐瞒          | 掌握关键信息，却未传递给其他Agent        | 0.8%  |
| FM-2.5 | 忽略其他Agent输入 | 收到信息或建议后没有采用                 | 1.9%  |
| FM-2.6 | 推理—动作不一致   | 推理结论与实际消息、工具调用或行动不一致 | 13.2% |

### 简要现象与原因

主要表现为**推理与行动不一致、任务跑偏、缺少信息时不澄清，以及关键信息未被传递或采用**。原因不仅是通信格式问题，还可能来自**Agent无法判断其他成员的信息需求、只关注局部任务、消息内容不完整，以及工作流缺少确认和反馈机制**。

------

## FC3：任务验证问题，占23.5%

这类失败与结果检查和质量控制有关，包括任务尚未完成便结束、没有充分验证结果，以及错误地把不正确结果判定为正确。

| 编号   | 失败模式           | 含义                               | 比例 |
| ------ | ------------------ | ---------------------------------- | ---- |
| FM-3.1 | 过早终止           | 任务尚未真正完成就提前结束         | 6.2% |
| FM-3.2 | 未验证或验证不完整 | 没有检查结果，或遗漏关键功能和条件 | 8.2% |
| FM-3.3 | 错误验证           | 验证方法、标准或结论本身错误       | 9.1% |

### 简要现象与原因

主要表现为**任务尚未完成就宣布结束、只进行表面检查，以及错误地判定结果通过验证**。原因通常是**验证流程过于简单、只检查语法或运行状态而忽略高层目标、测试覆盖不足，以及验证器缺少独立证据或重复了生成Agent的错误**。

------

# 4. 基于o1的LLM-as-a-Judge自动标注

## 4.1 为什么需要自动标注？

人工标注1642条长轨迹成本过高，因此作者让OpenAI o1充当评审员，自动判断轨迹中出现了哪些MAST失败模式。

### 输入

```
14种失败模式定义
+ 少量人工标注示例
+ 待分析的MAS执行轨迹
```

### 输出

```
多个失败模式标签
+ 标签判断理由
+ 任务是否完成
+ 失败模式数量
+ 轨迹整体总结
```

因此，它本质上是一个：

> **定义驱动的长文本Few-shot多标签分类任务。**

------

## 追问二：为什么使用o1，而不直接做监督学习？

论文明确说明的是：人工标注大量轨迹过于昂贵，需要一种可扩展标注方式。

根据论文流程，还可以合理推断出以下原因。

### 缺少足够人工标签

研究开始时：

- MAST分类尚未建立；
- 类别定义仍在调整；
- 高质量人工标签很少；
- 低频类别缺少正样本。

监督学习需要大量稳定的“轨迹—标签”训练对，但作者当时没有这些数据。

### 标注数据本身正是论文要构建的产物

```
训练监督分类器需要大量标签
→ 大量标签又需要专家人工标注
→ 人工标注正是作者希望降低的成本
```

### 分类体系仍在变化

Few-shot方法只需要修改：

- 类别定义；
- Prompt；
- 人工示例。

监督学习则可能需要重新标注并重新训练。

### 需要理解长距离交互关系

例如同样表现为“没有使用信息”，背后可能是：

- 信息隐瞒；
- 忽略输入；
- 历史丢失；
- 未请求澄清。

这需要分析完整交互，而不是只识别关键词。

------

## 追问三：这是不是本质上的Few-shot问题？

**是。**

更准确地说，是：

> **基于自然语言类别定义和少量人工案例的Few-shot长文本多标签分类。**

Few-shot示例的主要作用，是告诉o1作者如何处理模糊边界，例如：

- 对话重置与历史丢失；
- 未验证与错误验证；
- 信息隐瞒与忽略输入。

------

## 追问四：使用LLM是不是就是微调LLM？

**不是。**

本文没有更新o1的参数，只是在推理时把定义和示例放入上下文。

| 对比项         | Few-shot Prompting | 监督微调   |
| -------------- | ------------------ | ---------- |
| 示例位置       | 当前Prompt上下文   | 训练数据集 |
| 是否反向传播   | 否                 | 是         |
| 是否更新参数   | 否                 | 是         |
| 是否产生新模型 | 否                 | 是         |
| 分类变化后     | 修改Prompt         | 重新训练   |

核心区别是：

> **Few-shot把分类规则放进上下文；微调把分类规则写进模型参数。**

| 方法           | 主要回答的问题          | MAST的区别                 |

MAST的核心贡献不是找到“唯一根因”，而是提供一套：

> **可跨系统复用的失败描述语言。**

# 6. 实验结果

## 6.1 不同底层模型产生不同失败分布

固定MetaGPT和ProgramDev-v2：

| 类别             | Claude 3.7 | GPT-4o |
| ---------------- | ---------- | ------ |
| FC1 系统设计问题 | 63         | 38     |
| FC2 智能体间失配 | 58         | 47     |
| FC3 任务验证问题 | 83         | 77     |

GPT-4o在任务遵从和协作方面失败更少，但验证问题仍然明显。

------

## 6.2 系统架构同样重要

固定GPT-4o和ProgramDev-v2：

| 类别 | ChatDev | MetaGPT |
| ---- | ------- | ------- |
| FC1  | 118     | 38      |
| FC2  | 116     | 47      |
| FC3  | 30      | 77      |

结论：

- MetaGPT的SOP结构更有利于任务和角色遵从；
- ChatDev有明确测试与审查阶段，因此验证失败更少；
- 不同架构存在明显权衡，而不是某一个系统全面更优。

------

## 6.3 系统干预实验

### ChatDev

| 配置       | ProgramDev-v0 | HumanEval |
| ---------- | ------------- | --------- |
| 原始系统   | 25.0%         | 89.6%     |
| 改进提示词 | 34.4%         | 90.3%     |

主要修改包括：

- 明确角色上下级关系；
- 只有高权限Agent可以终止对话；
- 从DAG改为循环工作流；
- CTO确认所有审查完成后才结束。

在ProgramDev-v0上，拓扑修改提高了 **15.6个百分点**。

### AG2

| 配置       | GPT-4      | GPT-4o     |
| ---------- | ---------- | ---------- |
| 原始系统   | 84.75±1.94 | 84.25±1.86 |

# 7. 论文的主要洞见

## 洞见一：更强模型不能解决全部失败

模型升级可以减少部分任务遵循和协作问题，但验证失败仍然普遍存在。

## 洞见二：通信协议不是全部答案

标准消息格式可以减少歧义，但不能保证Agent知道：

- 对方缺少什么信息；
- 哪些信息必须传递；
- 收到信息后是否真正采用。

## 洞见三：需要多层验证

仅验证代码编译或格式正确远远不够，还需要：

```
语法检查
→ 执行检查
→ 功能检查
→ 边界情况检查
→ 高层任务目标检查
```

## 洞见四：成功轨迹也可能存在失败模式

有些轨迹虽然最终成功，但仍包含：

- 不完整验证；
- 错误验证；
- 不必要的重复。

这说明系统可能是“碰巧成功”，而不是流程可靠。
